# Appliance Store REST API (BE2_APIFromSpec)

A RESTful HTTP API for an appliance store built with Go, PostgreSQL, Gorilla Mux, and Swagger (OpenAPI 3.0/2.0).

---

## 🏛 Architecture & Design Patterns

The project follows a clean, layered architecture with separation of concerns:

```
src/
├── cmd/ (or main.go entry point)
├── internal/
│   ├── config/      # Application configuration (.env, environment variables)
│   ├── database/    # PostgreSQL connection pooling and DDL migrations
│   ├── models/
│   │   ├── dao/     # Data Access Objects (DAL - database row mapping)
│   │   └── dto/     # Data Transfer Objects (DTL - API request/response contracts)
│   ├── mappers/     # Conversion between DAO and DTO layers
│   ├── repository/  # Repository pattern (Database abstraction layer)
│   ├── handlers/    # HTTP Controllers with request validation & status codes
│   └── router/      # Gorilla Mux router with logging & recovery middlewares
├── docs/            # Swagger/OpenAPI specifications generated by swag
├── scripts/         # SQL schema definition
├── tests/           # Integration tests covering 100% of required endpoints
└── Makefile         # Build, test, run, and swagger generation automation
```

### Key Architectural Principles
1. **Repository Pattern**: All database operations are abstracted behind clean Go interfaces (`ClientRepository`, `ProductRepository`, `SupplierRepository`, `ImageRepository`, `AddressRepository`).
2. **DAO (Data Access Objects)**: Encapsulates database tables and SQL row scanning.
3. **DTO (Data Transfer Objects)**: Strictly validates external client input and controls exposed response fields.
4. **Mappers**: Explicit translation functions converting DAOs to DTOs and vice versa.
5. **RESTful Methodology**: Proper usage of HTTP verbs (`GET`, `POST`, `PUT`, `DELETE`, `PATCH`) with standard HTTP status codes (`200`, `201`, `400`, `404`).

## 🗄 Relational Database & Normal Forms

The database schema is strictly designed to satisfy **1NF, 2NF, 3NF, and BCNF**:

- **1NF (First Normal Form)**: All attributes contain atomic values (no repeating groups, arrays, or comma-separated lists). Every table has a primary key (`UUID`).
- **2NF (Second Normal Form)**: Satisfies 1NF, and all non-key attributes are fully functionally dependent on the entire primary key (`id`).
- **3NF (Third Normal Form)**: Satisfies 2NF, and there are no transitive dependencies. Addresses are extracted into their own table (`addresses`) referenced via foreign keys (`address_id`). Images are normalized into their own table (`images`).
- **BCNF (Boyce-Codd Normal Form)**: For every functional dependency $X \to Y$, $X$ is a superkey.

### Optimal DBMS Types Used:
- Identifiers: `UUID` (Primary keys generated via `gen_random_uuid()`)
- Money/Price: `NUMERIC(12, 2)` (eliminates floating-point rounding errors)
- Available Stock: `INTEGER` (with `CHECK (available_stock >= 0)`)
- Images: `BYTEA` (binary storage in PostgreSQL)
- Dates: `DATE` for birthdays, `TIMESTAMP WITH TIME ZONE` for timestamps
- Text: `VARCHAR(100)` / `VARCHAR(255)` with sensible length constraints

## 🚀 Getting Started

### Prerequisites
- Go 1.20+
- PostgreSQL running locally or in Docker

### Configuration
Configure connection settings via environment variables or `.env`:

```env
PORT=8080
DB_HOST=localhost
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=store_db
DB_SSLMODE=disable
```

### Running the Application
From the repository root or `src/`:

```bash
# Run server
make run

# Build binary
make build

# Run comprehensive integration test suite
make test

# Regenerate Swagger documentation
make swagger

# Clean built binaries
make clean
```

## 📡 API Endpoints Overview

All endpoints start with the prefix `/api/v1/`.

### 1. Clients (`/api/v1/clients`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/clients` | Add a client (JSON body with address) |
| `GET` | `/api/v1/clients` | Get all clients (with optional `limit` & `offset`) |
| `GET` | `/api/v1/clients/search` | Get clients by `client_name` and `client_surname` |
| `GET` | `/api/v1/clients/{id}` | Get client by ID |
| `PUT`/`PATCH` | `/api/v1/clients/{id}/address` | Change client address |
| `DELETE` | `/api/v1/clients/{id}` | Delete client by ID |

### 2. Products (`/api/v1/products`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/products` | Add a product (JSON body) |
| `GET` | `/api/v1/products` | Get all available products (`available_stock > 0`) |
| `GET` | `/api/v1/products/{id}` | Get product by ID |
| `PATCH` | `/api/v1/products/{id}/decrease` | Decrease quantity (`amount` in body or query) |
| `DELETE` | `/api/v1/products/{id}` | Delete product by ID |

### 3. Suppliers (`/api/v1/suppliers`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/suppliers` | Add a supplier (JSON body with address) |
| `GET` | `/api/v1/suppliers` | Get all suppliers |
| `GET` | `/api/v1/suppliers/{id}` | Get supplier by ID |
| `PUT`/`PATCH` | `/api/v1/suppliers/{id}/address` | Change supplier address |
| `DELETE` | `/api/v1/suppliers/{id}` | Delete supplier by ID |

### 4. Images (`/api/v1/images`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/images` | Add image (`product_id` + image bytes via multipart/JSON/stream) |
| `GET` | `/api/v1/products/{id}/image` | Get image of specific product (returns `application/octet-stream` download) |
| `GET` | `/api/v1/images/{id}` | Get image by image ID (returns `application/octet-stream` download) |
| `PUT`/`PATCH` | `/api/v1/images/{id}` | Replace image (replaces byte array with new string/data) |
| `DELETE` | `/api/v1/images/{id}` | Delete image by ID |
