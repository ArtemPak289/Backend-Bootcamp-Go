A production-grade RESTful HTTP API service for an appliance retail store built with **Go**, **PostgreSQL**, **Gorilla Mux**, and **Swagger (OpenAPI 3.0)**. The service implements Clean Layered Architecture, the Repository Pattern, strict Data Access Object (DAO) and Data Transfer Object (DTO) separation, and a relational database schema normalized to BCNF (Boyce-Codd Normal Form).

---

## 🏛 Architecture & Design Patterns

The project follows a clean, layered architecture with strict separation of concerns:

```
BE02-Store-REST-API/
├── main.go                  # Application entry point & server lifecycle
├── go.mod / go.sum          # Go module definitions
├── Makefile                 # Build, test, run, and swagger generation automation
├── schema.sql               # PostgreSQL DDL migrations & indexes
├── .env.example             # Configuration template
├── internal/
│   ├── config/              # Application configuration (.env loader)
│   ├── database/            # PostgreSQL connection pooling (sql.DB) & migrations
│   ├── models/
│   │   ├── dao/             # Data Access Objects (database row structures)
│   │   └── dto/             # Data Transfer Objects (API request/response contracts)
│   ├── mappers/             # Conversion functions between DAO and DTO layers
│   ├── repository/          # Repository pattern (Database abstraction interfaces)
│   ├── handlers/            # HTTP Controllers with input validation & status codes
│   └── router/              # Gorilla Mux router with logging & recovery middlewares
├── docs/                    # Swagger/OpenAPI specifications generated by swag
├── tests/                   # Integration test suite covering all endpoints
└── Store_API.postman_collection.json # Ready-to-import Postman API collection
```

### Key Architectural Principles
1. **Repository Pattern**: All database operations are abstracted behind clean Go interfaces (`ClientRepository`, `ProductRepository`, `SupplierRepository`, `ImageRepository`, `AddressRepository`).
2. **DAO / DTO Separation**: Internal database representations (DAO) never leak into external HTTP responses. All contracts are validated through DTOs.
3. **Explicit Mappers**: Centralized conversion functions translate models cleanly without runtime reflection overhead.
4. **Idempotency & RESTful Verbs**: Proper semantics using `GET`, `POST`, `PUT`, `PATCH`, and `DELETE` with standard HTTP status codes (`200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found`).

## 🗄 Relational Database & Normalization

The database schema is strictly designed to satisfy **1NF, 2NF, 3NF, and BCNF**:

- **1NF (First Normal Form)**: All attributes contain atomic scalar values. Every table defines an immutable primary key (`UUID`).
- **2NF (Second Normal Form)**: Meets 1NF, and all non-key attributes are fully functionally dependent on the entire primary key.
- **3NF (Third Normal Form)**: Meets 2NF, and eliminates all transitive dependencies. Addresses are decoupled into a dedicated `addresses` table referenced via foreign keys (`address_id`). Images are normalized into their own table (`images`).
- **BCNF (Boyce-Codd Normal Form)**: For every non-trivial functional dependency $X \to Y$, $X$ is a superkey.

### Optimal DBMS Data Types Used:
- **Identifiers**: `UUID` (Primary keys generated via `gen_random_uuid()`)
- **Monetary Values / Pricing**: `NUMERIC(12, 2)` (eliminates binary floating-point rounding errors)
- **Stock Quantity**: `INTEGER` (guarded by `CHECK (available_stock >= 0)`)
- **Binary Media**: `BYTEA` (safe binary storage for image blobs)
- **Timestamps**: `TIMESTAMP WITH TIME ZONE`

## 📡 API Endpoints Overview

All endpoints are versioned under `/api/v1/`:

### 1. Clients (`/api/v1/clients`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/clients` | Register a new client (JSON body with address) |
| `GET` | `/api/v1/clients` | List all clients (with `limit` & `offset` pagination) |
| `GET` | `/api/v1/clients/search` | Search clients by `client_name` and `client_surname` |
| `GET` | `/api/v1/clients/{id}` | Retrieve client profile by UUID |
| `PUT`/`PATCH` | `/api/v1/clients/{id}/address` | Update client physical address |
| `DELETE` | `/api/v1/clients/{id}` | Delete client by UUID |

### 2. Products (`/api/v1/products`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/products` | Create an inventory product |
| `GET` | `/api/v1/products` | Query all active products (`available_stock > 0`) |
| `GET` | `/api/v1/products/{id}` | Retrieve product details by UUID |
| `PATCH` | `/api/v1/products/{id}/decrease` | Decrease available stock count |
| `DELETE` | `/api/v1/products/{id}` | Remove product by UUID |

### 3. Suppliers (`/api/v1/suppliers`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/suppliers` | Register an appliance supplier |
| `GET` | `/api/v1/suppliers` | List all suppliers |
| `GET` | `/api/v1/suppliers/{id}` | Retrieve supplier profile by UUID |
| `PUT`/`PATCH` | `/api/v1/suppliers/{id}/address` | Update supplier address |
| `DELETE` | `/api/v1/suppliers/{id}` | Remove supplier by UUID |

### 4. Images (`/api/v1/images`)
| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/v1/images` | Upload image blob for a product |
| `GET` | `/api/v1/products/{id}/image` | Download product image (`application/octet-stream`) |
| `GET` | `/api/v1/images/{id}` | Download image by image UUID |
| `PUT`/`PATCH` | `/api/v1/images/{id}` | Replace image binary data |
| `DELETE` | `/api/v1/images/{id}` | Delete image by UUID |

## 🚀 How to Build & Run

### 1. Configuration
Copy `.env.example` to `.env`:
```bash
cp .env.example .env
```
Default connection parameters:
```env
PORT=8080
DB_HOST=localhost
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=store_db
DB_SSLMODE=disable
```

### 2. Running with Make
```bash
# Run the application locally
make run

# Build the executable binary
make build

# Run comprehensive integration test suite
make test

# Regenerate Swagger OpenAPI specifications
make swagger

# Clean build artifacts
make clean
```
